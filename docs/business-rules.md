# Business rules

BR-01 to BR-20 and REQ-IN-01 to 08.

| Rule | Statement | Owning module | Enforced in |
|---|---|---|---|
| BR-01 | A multi-channel order is split automatically at submission into independent sub-orders, each with its own number, invoice, route and rep. | Ordering | Layer 2 |
| BR-02 | The supply channel name is not disclosed to the retailer before the sub-order is confirmed. | Ordering / Core | Layer 2 |
| BR-03 | The rep name and phone are not disclosed before the order reaches on_the_way. | Delivery | Layer 3 |
| BR-04 | The price is frozen on the order at submission and is unaffected by any later price-list change. | Pricing | Layer 2 |
| BR-05 | Stock reservation starts at confirmation; the actual deduction happens at handover to the rep. | Inventory | Layer 3 |
| BR-06 | Cancellation by the retailer is permitted in the pending state only. | Ordering | Layer 2 |
| BR-07 | The cart is emptied automatically after a successful submission and held locally before it. | Ordering | Layer 2 |
| BR-08 | A composite offer is indivisible on add, remove and return. | Promotion | Layer 2 |
| BR-09 | An invoice discount applies only to the portion of the multi-channel order belonging to that channel. | Promotion / Finance | Layer 2 |
| BR-10 | A posted invoice cannot be edited; corrections are made by a linked credit or debit note. | Finance | Layer 3 |
| BR-11 | Every payment is documented by a unique receipt number shared between the rep and retailer apps to prevent double entry. | Finance / Core | L1 (idempotency basis) |
| BR-12 | A rep may not exceed the discount cap or the cash-collection cap set for them. | Delivery / Finance | Layer 3 |
| BR-13 | An accepted return re-enters stock according to the warehouse inspection, not the requester claim. | Returns / Inventory | Layer 3 |
| BR-14 | The retailer sees a logical availability state and never the numeric stock quantity. | Inventory / Catalog | Layer 2 |
| BR-15 | Products, prices and offers are always filtered by three criteria together: zone, activity type and retailer group. | Catalog / Pricing | Layer 2 |
| BR-16 | Every operation that changes financial or inventory data is written to the audit log and is never hard deleted. | Core | L1 |
| BR-17 | A read notification is hidden from the counter but is not deleted from the log. | Notification | Layer 4 |
| BR-18 | Date and time are presented in Arabic format in local Damascus time across every interface. | Core | L1 |
| BR-19 | An order may not be assigned to a rep who is off duty or outside their zones. | Ordering / Delivery | Layer 3 |
| BR-20 | An offer that expires or runs out of quota is removed from unsent carts with a notice before confirmation. | Promotion | Layer 2 |
| REQ-IN-01 | The receipt number is generated by one side and read by the other; two payments with the same number are never accepted, even across repeated sync. | Core / Finance | L1 (idempotency basis) |
| REQ-IN-02 | Handover requires dual confirmation: stock is not deducted and the state does not move to on_the_way on one confirmation alone. | Fulfillment | Layer 3 |
| REQ-IN-03 | An assigned order appears in the rep accept queue; rejection returns it to unassigned with a reason and an immediate channel alert. | Ordering | Layer 3 |
| REQ-IN-04 | A return may be raised by either app, decided only by the channel, and its physical condition is determined by the warehouse. | Returns | Layer 3 |
| REQ-IN-05 | Both parties see the same delivery line list and any quantity edit changes the invoice amount for both. | Delivery | Layer 3 |
| REQ-IN-06 | Channel and rep identity are withheld at the data layer, not at the presentation layer. | Core / Tenancy | L1 (enforced by design) |
| REQ-IN-07 | Pricing is computed on the server only; no local pricing logic is permitted beyond a clearly marked temporary estimate. | Pricing | Layer 2 |
| REQ-IN-08 | The multi-channel split happens on the server at submission; the retailer sees one order and each channel sees only its part. | Ordering | Layer 2 |
